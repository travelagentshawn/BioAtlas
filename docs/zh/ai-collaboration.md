# 多 AI 协作协议

BioAtlas 不绑定任何单一模型或平台。约定写在仓库里，任何 AI（或人）读完这几页就能接手。

## 入口文件

| 文件 | 给谁 |
| --- | --- |
| [`AGENTS.md`](repo:AGENTS.md) | 通用的 AI 编码代理（多数工具会自动读取） |
| [`llms.txt`](repo:llms.txt) | 只想读取数据的 AI：一页纸的地图 |
| [`manifest.json`](api:manifest.json) | 机器可读入口，含所有端点 |
| 本说明书 | 细节 |

## 角色与所有权

| 角色 | 可以改 | 不要改 | 完成标准 |
| --- | --- | --- | --- |
| **数据代理** | `data/`、`schema/`、`tools/lib`、`tools/build-api.mjs` | `ui/` | `npm run validate`、`npm run build:api` 通过 |
| **界面代理** | `ui/` | `data/`、`schema/` | `npm run build:ui` 通过，页面在 `?api=` 指向的任意合格 API 上工作 |
| **文档代理** | `docs/`、`README.md`、`AGENTS.md`、`llms.txt` | — | `npm run build:docs` 通过，链接有效 |
| **契约变更** | `contract/` | — | 需要数据与界面双方确认，见[API 契约](api-contract.md) |

不同代理可以**并行工作在不同目录**，在契约上汇合；不需要共享对话上下文。

## 交接规则

1. **以仓库为唯一事实来源。** 不要依赖“我之前说过”；把决定写进 PR 描述、文档或 `docs/zh/roadmap.md` 的待办。
2. **小而完整的 PR。** 一个 PR 只做一件事，通过 `npm run check`。
3. **PR 描述模板：** 目的；改动的目录；是否影响契约；怎么验证；仍待人工核对的内容。
4. **提交信息署名：**如果由 AI 编写，请在提交末尾用 `Co-Authored-By: <模型名与版本> <邮箱>` 标明，便于追溯。可以是任何模型。
5. **不要覆盖他人的未合并工作。** 先拉取最新 `main`，冲突时保留双方意图并说明。
6. **不确定就标注，不要编造。** 无法核实的引用、年代、等级：保持 `seed`，并在 PR 中列为待核对。

## 给 AI 的快速上手清单

1. 读 `AGENTS.md`，再读[数据模型](data-model.md)。
2. `npm run validate`，确认基线是绿色。
3. 只在你的角色范围内改动。
4. 改完运行 `npm run check`。
5. 在 PR 里写清楚核对了什么、没核对什么。

## 为什么用这种方式

不同模型擅长不同事情：有的擅长检索与核对文献，有的擅长前端，有的擅长写作。解耦的目录、机器可校验的契约和显式的审核状态，让它们可以互相审查而不必互相信任。
